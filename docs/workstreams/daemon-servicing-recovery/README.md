# Daemon servicing and recovery: design for review

Status: target direction accepted for design; production implementation is not approved. See [the concrete hosting proposal](hosting-proposal.md) for the narrowed recommendation and three material choices. Local design only, 2026-11-04. No installer, launchd, daemon, network or privileged operations performed. Remote issues, PRs and CI remain paused. This document is the local problem/decision record instead of a remote issue.

## Problem and scope

Fresh unsigned LOCAL DEV packaging deliberately rejects existing installations. Safely extending it requires an owner that survives GUI closure, fences concurrent starts, proves cleanup and process exit before replacing bytes, and recovers an interrupted transaction. Root ownership is integrity protection, not delivery trust. No candidate, trusted Apple pin or `apple_reviewed: true` is established here; L's provenance work remains independent and blocking.

Goal: explicitly requested fresh install, update, rollback and uninstall, plus conservative recovery after GUI exit, servicing-owner crash, daemon crash and reboot. No automatic VPN restoration, account reassignment, forced cleanup, release delivery or service-manager selection is approved by this design.

- Core object `7cc55f07ce2c48be4071b155c3dd58cf925a88ae`, read using git show from registered `research-apple-core-provenance` repository, without changing that worktree: `cmd/bimeron/daemon_unix.go`, `internal/control/server.go`, `daemon_guards.go`, `socket_unix.go`, `core/engine.go`. No inspection of L's uncommitted changes or claims about its outcome.

Core source serializes start/stop/shutdown admission. Guarded start/stop validate instance/session. Legacy unguarded commands remain possible. Successful shutdown sets `closing` under the command mutex after Engine.Stop; subsequent start is rejected, and the reply path cancels Serve. However the guard validator accepts instance only for start/stop, so shutdown cannot currently bind to an expected instance, including the idle case. Serve attempts Engine.Stop on exit even after context cancellation; Engine.Stop waits for run completion or its context. These are source contracts, not proof of live DNS/route/utun restoration. Listener closure releases daemon.lock before deferred engine cleanup completes: a free lock or missing socket is insufficient evidence of cleanup or full process exit.

Current macOS transport permits only hello/status/start/stop and its response model omits Core build/capability details. Neither journal, servicing fence, guarded shutdown, process-exit proof nor cross-reboot cleanup reconciliation is supplied by that adapter. Developer recovery records must not be promoted into authenticated cleanup receipts.

## Options and recommendation

1. Keep fresh-only packaging; service existing installs manually only after a separately designed procedure. Smallest immediately feasible boundary and safest current behavior. Drawback: no supported update, rollback or uninstall; partial installs require investigation. Retain this boundary until acceptance below passes.
2. Add a narrowly scoped privileged servicing owner with a durable transaction record, plus extend existing Core admission/shutdown. Recommended target, subject to agreement. Reuse Core for all network lifecycle work and the fixed launchd service identity. Drawbacks: new privileged code and authorization surface, crash-consistency testing, Core protocol work, and a recovery entry path independent of the GUI. The choice of an authorized one-shot tool with recovery entry versus a resident management helper remains open; do not assume either exists.
3. Use package scripts or GUI as the transaction owner. Fewer initial components, but GUI death and concurrent clients leave no durable authority. A package script that implements locking, journal, recovery and authorization effectively becomes option 2. Do not expand G's current shell checks into a servicing protocol by implication.

Recommendation is a staged capability, not immediate production implementation. A generic broker, new daemon engine or separate network cleanup implementation is unnecessary. A durable recovery mechanism is necessary; its hosting and reboot ordering need agreement and platform validation.

## Ownership and identity

Core owns sessions, network teardown and network recovery. Launchd owns service process management; registration success, a PID, a vanished socket, exit zero or a status cache are not readiness/cleanup proof. A proposed privileged servicing owner owns file/service transactions and journal; it calls Core and verifies outcomes. GUI is a requester/observer: closing the app neither aborts servicing nor disconnects an existing session by itself. Reopening queries operation identity and fresh daemon state; it never replays a lost start, stop or update automatically.

Use one machine-wide fixed installation identity associated with `org.bimeron.core`, not a user profile, PID or binary digest. Separate identities: durable installation ID, random operation ID, operation generation, OS boot identity, daemon instance and Core session ID. Requests carry expected installation/operation generation; duplicate operation requests return existing results. A timed-out mutation has unknown outcome until reconciled, not permission to retry with a new ID.

A protected persistent service-transaction lock serializes all install/update/rollback/uninstall/recovery entry points across users/processes. Hold its descriptor for the transaction; never unlink/recreate a lock file to clear a stale PID. Verify ancestry, inode/type/ownership/ACLs before use. Lock release after owner death permits journal reconciliation, not a new unrelated operation. Lock order: servicing lock, Core admission/fence, then file/service changes. GUI actor locks and Core daemon.lock serve different purposes and cannot substitute. A malicious privileged writer is outside this integrity boundary.

Proposed single-user control policy preserves G's explicitly selected numeric local UID. Root may service; unrelated users, another login session and the current foreground user do not implicitly gain control. Account deletion, UID reuse and changed account mapping block mutation pending explicit reauthorization; recheck binding on servicing/recovery. Decide whether other local sessions may read sanitized status; default recommendation is owner/root only. Do not broaden socket mode or infer authorization from GUI ownership. Uninstall is machine-wide and requires separately authorized servicing intent even when requested by the control UID.

## Required Core contract, not existing APIs

Extend the existing shutdown path with atomic expected-instance admission, an optional expected-session precondition for active state, and an operation/fence identity. It must work while idle and reject all start entry paths, including legacy clients, while servicing. Stale instances/sessions must reject without affecting a different session. Require explicit authorization to interrupt the observed active session before admission. A mismatched session returns to review; do not stop an unexpected replacement session.

Successful admission closes new starts under the same command mutex before teardown, then runs Stop. Expose a queryable result tied to operation, instance and boot, proving disconnected plus inactive after teardown. If cleanup fails, keep admission closed and preserve error/recovery information; reopening admission requires explicit verified recovery. Shutdown exits only after recording an authoritative outcome accessible to servicing. A response alone followed by a crash cannot be the only receipt. Persistence, authenticity and schema of that receipt are an API/design gap, not functionality of the current developer record.

On daemon crash/reboot with no valid cleanup outcome, a Core recovery API must reconcile its owned DNS/routes/resources using retained evidence before declaring inactive/clean. A new empty engine's disconnected status does not prove previous-instance cleanup. Core must define what can actually be recovered, how conflicting external network changes are handled, and when human recovery is required. Servicing never guesses route deletions or restores a generic DNS snapshot. No force-kill shortcut turns unknown cleanup into success.

## Transaction state model

States below describe servicing, separate from Core's VPN states. Persistent phase is an intent marker, not proof the corresponding side effect completed. Every restart compares journal with protected files, service identity and fresh Core evidence.

1. **Idle / absent or installed:** no outstanding transaction. Installed readiness is an independently observed property, never a persisted boolean.
2. **Prepared:** trusted/explicitly untrusted-DEV classification retained; candidate validated in protected same-volume staging; previous approved artifact set retained. Write durable operation intent before mutations. No downtime yet.
3. **Quiescing:** exclusive transaction ownership, Core maintenance admission fenced, stop authorized for exact instance/session, cleanup result pending. Timeout/error becomes **CleanupBlocked**, never permission to replace.
4. **CleanStopped:** Core cleanup confirmed for that fenced instance and full process exit independently confirmed; prevent service restart throughout replacement. Exact exit observation/service disable method is a platform acceptance gap. A disconnect reply alone does not suffice.
5. **Replacing:** persist selected old/new artifact manifests and recovery action before each change; publish binary, plist and metadata as a recoverable set. Individual renames are not an atomic multi-file transaction. No registration/start until the full set is verified. Fresh install skips old-daemon cleanup only after positively establishing no prior installation or recovery residue.
6. **Verifying:** register/start control daemon with start admission still fenced; fresh authenticated handshake proves selected build, compatibility and recovery status. No VPN start. Failure enters **RollbackPending**, never a successful install.
7. **Committed:** durably record verified artifact generation and operation outcome, then release maintenance and transaction ownership. Preserve prior artifact until retention policy permits deletion. Reopening GUI can observe completed outcome without restoring VPN.
8. **CleanupBlocked / RecoveryRequired:** retain journal, old artifacts and Core evidence; deny new VPN starts and unrelated servicing; present actionable bounded failure. No automatic loop. Only read-only reconciliation or explicit scoped recovery.
9. **RollbackPending:** if candidate ever ran, fence/stop it and prove its cleanup and exit first. Revalidate previous artifact against current trust/compatibility policy; restore the full previous set with the same staged protocol, then fresh handshake. If unavailable, revoked, incompatible or cleanup unknown, remain RecoveryRequired. Rollback is not permission to downgrade through policy.
10. **Removing / Removed:** follow quiescing and CleanStopped; durably mark removal intent; unregister and verify service absence; delete only known installation-owned artifacts after identity checks; retain minimal removal result as policy permits. Stop failure leaves installation and recovery tools intact. Uninstall completion requires known cleanup and no restart path, not merely missing files.

Persist records under a proposed protected root-owned state directory, separate from user profiles (candidate `/var/db/bimeron/servicing`; exact namespace must be coordinated with Core). Record schema/version, installation and operation identities, phase/generation, boot/instance/session, authorized intent/owner binding, old/new digests and compatibility records, completed steps and bounded errors. No secrets, config contents or credentials. Atomic record publication and file/directory durability must be specified and power-loss tested; unsupported/corrupt schema blocks mutation. A journal is not a cleanup certificate or trust root.

## Interruption and security rules

Before replacement, recheck ancestor protection, leaf type, root:wheel ownership, expected modes, conservative deny-only/no ACL policy, hashes and file identity. Reject symlinks in every component, unexpected hard links/types, writable ancestors and substitutions. Use descriptor-relative no-follow operations in protected staging and compare validated/opened identities; shell lstat-then-copy checks are insufficient TOCTOU protection. Keep staging on the target filesystem; no user-selected root destination or recursive deletion of arbitrary paths. Revalidate before publication, restart, rollback and deletion. Preserve G's fixed payload paths unless separately agreed. Root ownership and peer UID 0 do not authenticate exact executable bytes; build claims must be correlated with validated installed artifact/process identity using a separately verified mechanism.

Before any new side effect, recovery inspects durable intent and actual artifacts. Before quiescence it may discard only its own staging. During quiescence it queries the exact operation/instance; missing peer means unknown cleanup. During replacement it selects a complete validated set from journal, never whichever file exists. After publication but before commit, verify current candidate or restore approved prior set only after required cleanup. After commit, recover the outcome without repeating mutations. During removal, resume only known deletions; retain profiles regardless of intermediate phase.

Reboot invalidates instance-specific readiness and in-memory fences. Startup ordering must ensure the Core service cannot accept start while an unfinished servicing/recovery record exists. This requires Core startup gating or a validated service-management barrier; neither is implemented. Launchd RunAtLoad alone does not provide it. Recommendation: every Core startup checks maintenance/recovery state before mutation admission, with fail-closed behavior on unknown schema. Hosting and ordering remain decisions. Reboot never restores VPN automatically; future opt-in policy must explicitly cover profile validity, user authorization and credential handling.

Uninstall retains user profiles, settings, history and credentials by default, without reading/migrating them. Purging user data is a separate explicit per-user operation outside this scope. Retain Core recovery evidence when cleanup is unconfirmed; do not remove the only recovery-capable binary. Decide separately how long successful servicing receipts/artifacts are retained.

## Version, trust and readiness gates

Preflight both candidate and rollback: architecture and minimum OS, exact binary digest/revision, authenticated manifest/pin and review status for release delivery, app/Core protocol and capability compatibility, journal/receipt schema compatibility, supported recovery format and migration/downgrade policy. Compare structured compatibility policy, not version strings alone. No destructive data migration in this minimal design. LOCAL DEV remains an explicitly untrusted lane and cannot satisfy release acceptance. L's retained record is not assumed sufficient until reviewed; no pin or candidate is invented here.

Fresh readiness requires a new request ID on an authenticated current connection, current instance/boot, matching installed artifact generation/build, required guard/maintenance/recovery capabilities, no unresolved cleanup and disconnected/inactive state. Verify process identity independently of self-reported build fields. Old status, launchd bootstrap success, old hello or cached journal success cannot satisfy it. A candidate that cannot attest recovered prior resources stays blocked even if its engine is initially disconnected.

## Staged acceptance and failure injection

Stage A, offline specification/model: check that replacement/removal is unreachable without cleanup plus exit evidence; concurrent start cannot cross admitted maintenance; changed instance/session invalidates proof; operation retries are idempotent; unknown outcomes block. Model test evidence would validate only the model. No experiment was needed or run for this design.

Stage B, Core contract tests: race legacy and guarded starts against maintenance; active/idle/stale-instance shutdown; stop failure/cancellation; daemon death before receipt; corrupt/unknown recovery record; startup with unfinished transaction; conflicting network state. Require Core owners to define actual cleanup invariants and safe recovery failure outcomes.

Stage C, sandboxed filesystem/servicing adapter tests: two concurrent owners and users; reused PID/UID; lock-holder crash; symlink/ACL/hard-link substitution before every file use; altered candidate/backup; disk full and permission denial at each journal write/fsync/rename; interrupted binary/plist/metadata publication; missing backup; revoked rollback; incompatible schemas. Assert no arbitrary deletion, no mixed artifact set starts, and no user-data changes. Fake service status must be labeled synthetic.

Stage D, separately authorized disposable Mac: actual Installer authorization/account binding, service restart suppression and exact process-exit observation, fresh handshake/build correlation, crash/reboot at every durable boundary, GUI close/reopen, other-user login, disconnect error and failed recovery. Independently inspect actual DNS/routes/utun before/after using Core-defined evidence. Test no VPN auto-start across reboot, rollback and app reopen. Inject candidate handshake failure and candidate cleanup failure before rollback; fail safely when proof is unavailable.

Stage E, later release gate: trusted Apple pin/candidate/provenance resolution, compatibility review, signed delivery policy, CI and real-machine acceptance. None is satisfied by mock protocols, static plist checks, P's UI navigation, M's combined tests or this document. No benchmarks are relevant until a concrete implementation introduces measurable latency; bounded timeout behavior belongs in acceptance.
