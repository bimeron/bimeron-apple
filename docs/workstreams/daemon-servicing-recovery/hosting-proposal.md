# Concrete hosting proposal: unsigned DEV servicing first

2026-11-04. The user approved the three recommended constraints: separate root servicing LaunchDaemon with explicit root CLI for DEV; fail-closed manual recovery/reboot instead of same-boot adoption; future fresh-capable installations only, one backup, no owner self-update, and two-stage uninstall. Authorization now covers a pure offline model/protocol prototype and failure-injection tests. It does not cover production implementation or privileged execution. It supplements [the state model](README.md). No production files are changed.

## Recommended minimum

Keep G's unsigned fresh-only package as the initial delivery. Do not retrofit servicing onto existing G payloads: they lack the admission/startup fence and recovery contract. Future servicing-capable fresh installations would install a small **separate root LaunchDaemon**, a root command-line client, and a fence-aware Core. Existing installations without that contract remain unsupported, even if a newer package contains the new owner. This avoids claiming that an upgrade can safely install the very barrier it needs to perform that upgrade.

The proposed owner is a fixed-purpose file/service transaction executor, not a generic command broker. It never runs caller-selected commands, accepts arbitrary destination paths, reads profiles or implements network cleanup. Core remains directly managed as `system/org.bimeron.core`; no supervisor wrapper or Core child process is introduced.

Proposed fixed placement, for review:

- Owner executable `/Library/PrivilegedHelperTools/org.bimeron.servicing`, root:wheel 0755; service `/Library/LaunchDaemons/org.bimeron.servicing.plist`, root:wheel 0644; label `org.bimeron.servicing` in system domain.
- Existing G Core executable/plist/metadata paths retained. No Core payload replacement while Core can execute it.
- State `/var/db/bimeron/servicing`, root:wheel 0700, with no allow ACLs; `transaction.lock`, installation record, active journal, immutable operation outcomes, prior artifact set and Core result records. Exact shared namespace still needs Core-owner review before coding.
- Owner administrative socket `/var/run/bimeron-servicing.sock`, launchd-owned root:wheel 0600. Use launchd `Sockets` and `launch_activate_socket` (not a socket merely watched by path). Validate kernel peer UID 0 before parsing any command. Root directory ancestry remains protected.
- Owner: `RunAtLoad` once to inspect pending state, plus socket demand activation, no KeepAlive respawn loop. Stay alive while owning a transaction; idle exit is permitted. Owner restart on a later admin request performs reconciliation first. Boot inspection reports/holds incomplete work; it does not automatically start VPN or invent new authorization. No filesystem WatchPaths/PathState signaling.

A separate boot worker is unnecessary. Every fence-aware Core startup checks the durable installation/maintenance gate before opening mutation admission; no launchd ordering dependency. Core may expose read-only status while gated. Missing gate in an installation that requires it, corrupt/unknown schema, pending removal, unresolved Core recovery or a nonterminal operation all deny start. A new absent installation is created only by an explicit installer, not inferred from missing state. Direct/legacy Core start commands must enforce the same gate in Core, not only in the GUI.

This adds one small resident-capable process and its root IPC parser. It avoids moving Core under a supervisor, but loses `waitpid` as an exit-proof mechanism: the owner is not Core's parent. The nonchild exit observation below is a required acceptance item, not an implementation detail to gloss over.

## Why these alternatives are not the minimum here

A one-shot root CLI is smaller for individual operations, but needs another recovery/startup entry to survive reboot and has no durable service-side request identity after its caller dies. It is viable only if manual recovery after every interruption is accepted; recommend the single demand/boot owner instead.

A supervising owner that spawns Core could reap the exact child with waitpid. However it changes the established launchd/Core process arrangement, child failure handling, signal/process-group behavior and Core startup. Local launchd documentation says remaining process-group members are killed when their job dies by default. Do not add that lifecycle solely to avoid validating nonchild exit observation.

SMAppService is a later signed-distribution alternative, not an unsigned bootstrap shortcut. It ties helpers to an app bundle and introduces consent, registration and app-location handling. SMJobBless requires signed app/tool and reciprocal requirements and is deprecated. AuthorizationExecuteWithPrivileges is also deprecated. None is proposed for local DEV.

## Authorization: explicit administrator, no implicit GUI privilege

For the first servicing-capable DEV design, accept **only an explicitly invoked root CLI** talking to the root-only owner socket. A later separately authorized admin may invoke it using the machine's normal elevation procedure; no sudoers changes, setuid binary, custom Authorization database right, stored authorization blob or GUI password collection is proposed. This document executes none of those steps.

The client shows a bounded plan and submits explicit verb, installation ID, expected generation, candidate artifact-set digest and the exact observed instance/session the admin agrees to interrupt. The owner recomputes the plan from its protected staged bytes and returns a one-use short-lived plan token binding those fields. Commit must match the token and caller; changed generation, active session or artifact requires a new plan/confirmation. Cancel/timeout before commit causes no mutation. A root principal is already fully privileged; the token prevents accidental stale intent, not malicious root access.

Ordinary GUI/Core control remains restricted to G's configured single local UID (plus root under Core's existing policy). Persist and revalidate directory account identity as well as numeric UID; account deletion/reuse/change requires explicit admin rebind, never automatic reassignment to the foreground user. Same-UID processes share the control privilege in unsigned DEV: peer UID cannot prove which GUI executable sent a request. Do not describe this as app authentication. No servicing mutation is granted merely because that UID can start/stop VPN. Read-only servicing status is initially available through the root CLI; the GUI can show Core's sanitized maintenance state, without granting a second servicing endpoint.

Authorized committed intent is durable: operation ID, authorizing root principal/audit context available at admission, selected owner binding, allowed action/digests/session, and recovery policy. On process restart or reboot the owner may reconcile read-only and maintain the fence without new credentials. Recommendation: require a new explicit root `resume` or `rollback` approval before any post-crash artifact changes. This conservative manual resume trades unattended recovery for fewer ambiguous authorization rules. Completion after GUI/client closure continues if the owner itself remains alive. An IPC timeout must query the existing operation, never create a second one.

## Durable protocol and lock order

One protected `transaction.lock` inode persists for the installation lifetime. Acquire it exclusively before reading or changing journal/gate or submitting Core maintenance. Do not truncate or unlink it to break a lock; another owner waits/fails busy. Core does not acquire this lock: otherwise Stop can deadlock waiting on the caller. Owner-only operation order is transaction lock, durable gate/journal publication, Core command admission mutex, cleanup/exit, then filesystem/service changes. Core command admission must never wait for the owner lock.

The owner writes a durable maintenance intent **before** sending Core the shutdown request. Existing Core atomically rechecks the on-disk gate under its start-admission mutex; in-flight starts admitted earlier can exist, so maintenance must still match their actual instance/session. On mismatch leave gate closed, report new state and require fresh admin interruption consent. Future Core startups see the marker even if the owner crashed before IPC. Core does not clear the owner gate or edit owner journal.

Use a strict schema with installation UUID, schema version, monotonically increasing generation, operation UUID, action, phase/sequence, owner identity binding, boot/instance/session, complete old/new artifact-set digests, authorization scope, pending side effect and outcome references. No caller paths or credentials. Bound sizes and reject duplicate keys/unsupported versions. Core reads only a small versioned gate projection; this projection and its journal generation must be published consistently. Prefer a single authoritative record for phase/gate rather than independently updated booleans. Core results live separately and are bound to the exact generation and operation.

For each mutation: persist intent and verify durability, perform the idempotent effect, observe it, then persist outcome. Write new records in the protected directory, flush, atomically rename, and synchronize directory metadata using validated platform behavior; retain last valid generation. Local fcntl documentation describes F_FULLFSYNC, but this is not proof of directory/power-loss semantics. A storage/flush error stops progression. Never recover a successful phase solely from its recorded name; compare actual files/service state and result identities. Partial multi-file publication remains fenced until a complete validated set is restored. Corrupt/missing records in an installed system require recovery, not defaults.

## Proposed Core API delta

These names/fields are a proposed minimal contract, absent from 7cc55f0. Keep existing session API but add a **root-only maintenance channel**, separate from the owner-UID public socket. The servicing owner and Core authenticate root kernel peers. Bind both endpoints to protected fixed ancestry; peer UID 0 alone is not release provenance.

1. `maintenance_status`: returns supported contract/schema, installation and generation, boot/instance, explicit session ID/active flag, gate/operation identity, Core build details and previous recovery outcome. Missing session/evidence cannot satisfy servicing cleanup even though the current app helper permits absent Session.
2. `maintenance_shutdown`: expected installation/generation/operation, boot/instance and explicit expected session (or explicit idle expectation). Under the existing command mutex, validate root authorization and durable gate identity, reject stale expectations, seal all starts including legacy requests, then call Engine.Stop. Seal before Stop, unlike the present closing-after-success behavior. A failed Stop leaves admission sealed and exposes failure; it never silently reopens or switches profile.
3. A durable Core cleanup result: schema, installation/operation/generation, producing boot/instance/session, disconnected state, explicit inactive session, cleanup result and retained recovery-state identity. Publish success only after Core's actual teardown invariants pass and the record is durable. Exiting after a failed cleanup must not create a success receipt. Nonzero error, missing result, unexpected instance or stale generation blocks servicing. This is a root-protected local statement by the selected Core, not cryptographic attestation or proof against malicious root.
4. `maintenance_recover`: explicit root-authorized recovery for an existing gated operation. Run Core-owned recovery without VPN start and produce the same scoped result. It must use retained resource identities and detect external DNS/route changes; if safe recovery is impossible, report RecoveryRequired. A fresh empty engine's disconnected state is not recovery.
5. `maintenance_release`: only after the owner durably commits a verified installed generation, send expected current instance/generation; Core rereads terminal record and recovery state under admission mutex before reopening start. After a crash between commit and release, a fresh handshake/reconciliation may release the same committed generation; never reconstruct/replay a VPN start.

Core needs durable dirty-session/recovery evidence **before** acquiring/mutating network resources, not only when servicing begins. Reboot without an active servicing journal can still follow a daemon crash. If retained state cannot distinguish clean exit from interrupted network mutation, startup must remain recovery-gated. Defining what DNS/routes/utun recovery can guarantee belongs to Core owners; this proposal does not invent that evidence or imply existing developer records meet it.

## Full exit proof and restart exclusion

Before shutdown, connect to the current Core maintenance socket and obtain the kernel peer PID/audit identity (SDK exposes LOCAL_PEERPID/LOCAL_PEERTOKEN). Bind to boot plus process start time from process information, and expected Core instance. Register EVFILT_PROC/NOTE_EXIT before submitting maintenance_shutdown, recheck identity/instance after registration, and retain that observation through shutdown. Only a corresponding exit event, paired with the exact successful durable cleanup result, satisfies CleanStopped in the normal same-boot path. Do not waitpid a launchd-owned Core. Exit status is not cleanup evidence.

After durable gate publication, prevent reloading the Core launchd service during replacement using persistent service disable, checking the actual result. Disable does not replace the Core admission fence or stop an already running process. After cleanup receipt AND exact exit event, remove the old service registration before publication. Bootout success alone is not exit proof. No kill/kickstart -k fallback. The owner label remains running while Core is replaced; owner/plist self-update is excluded from the first protocol.

After publication, register the complete verified Core set, enable/start it explicitly for control readiness while the durable maintenance gate still denies VPN starts, then perform a fresh build/capability/recovery handshake. Only after commit/release may user start be admitted. These launchd steps are a proposed adapter sequence requiring disposable-Mac validation, not executed commands or a readiness guarantee. Preserve intentional prior disabled state; if the admin/user disabled the service independently, require explicit approval to enable instead of overwriting that choice.

If the observer/owner crashes and loses the exact exit event, do not synthesize it from PID absence, PID reuse, old journal or socket disappearance. Minimal first version holds RecoveryRequired and does not replace artifacts on that boot. Recommend an explicit reboot/recovery route: a new boot establishes that the previous boot's processes cannot still execute; a Core recovery-only run must separately prove resource cleanup before replacement resumes. If reboot is unacceptable, same-boot adoption with kernel identity/exit reconciliation becomes additional scope and needs its own proof/tests. New boot alone never proves network cleanup. A crash/reboot during cleanup therefore remains service downtime until explicit verified recovery.

## Update, rollback and removal policy

No downloaded/external executable is run for preflight. Copy approved bytes into root-protected same-volume staging and validate type/ancestry/mode/ACL/link count/digest/compatibility before use; open relative to verified directory descriptors and reject substitutions. Development assertions remain untrusted even when copied by root. A complete previous artifact set is retained before quiescence, never overwritten by staging. Support only the declared app/Core/gate/recovery schema compatibility matrix; no destructive migration or arbitrary version downgrade.

Candidate readiness failure may offer rollback to the retained previous approved set; require cleanup plus exit proof for any candidate that ran, then revalidate prior trust and compatibility. Revocation/incompatibility or missing evidence means blocked rollback, not a force option. Keep one previous successful artifact generation and current operation evidence in the first protocol; do not silently delete older unresolved recovery evidence. This retention policy is a proposal, not release trust policy.

Uninstall uses identical gate/cleanup/exit proof. Remove only the known Core artifact set and registration; retain profiles, settings, history, credentials and unresolved Core evidence. Recommended first stage removes Core but retains the inert recovery/servicing tool, its root-only endpoint and minimal outcome record until a separate finalization. Report that honestly as **Core removed; servicing tool retained**, not complete product uninstall. Full removal of the owner itself is an explicit final root administrative step after it has exited, with verified service absence and only known files deleted; never implement executable self-deletion or arbitrary recursive purge. Failed cleanup leaves recovery-capable binaries available. No automatic VPN restoration after update, rollback, reboot or GUI reopen.

## Local authoritative facility evidence and its limits

Read-only host evidence: macOS 26.5 (25F71); local SDK at `/Library/Developer/CommandLineTools/SDKs/MacOSX.sdk`. No network lookups, system configuration reads beyond version, service commands or API execution were needed.

- `/usr/share/man/man1/launchctl.1`: system-domain modification requires root; disable persists across boots; bootstrap/bootout operate on service definitions. No cleanup acknowledgement is specified.
- `/usr/share/man/man5/launchd.plist.5`: RunAtLoad launches once when loaded; Sockets uses launch_activate_socket; SockPathOwner/Group/Mode control Unix socket ownership/mode; KeepAlive may restart/throttle; WatchPaths/PathState are race-prone; ExitTimeOut can end in SIGKILL. These are not transaction or readiness primitives.
- SDK `usr/share/man/man2/kqueue.2`: NOTE_EXIT reports exit for an observed process; NOTE_EXITSTATUS is child-only. SDK `wait.2`: waitpid is for children. SDK `sys/un.h`, `libproc.h`, `sys/proc_info.h`: peer PID/token and process start-time facilities exist. Race-free association, executable provenance and post-crash behavior remain adapter acceptance work; no live exit proof was collected.
- SDK `fcntl.2`: F_FULLFSYNC requests stable-storage flushing; this does not by itself validate the proposed journal protocol on actual power loss.
- SDK ServiceManagement `SMAppService.h`: code signing required; applications containing LaunchDaemons must be notarized; registration/approval makes a daemon eligible to run. Unregister may kill and synchronous unregister does not wait for reaping. SDK `ServiceManagement.h`: signed app/tool requirements for deprecated SMJobBless. Security `Authorization.h`: deprecated AuthorizationExecuteWithPrivileges and explicit authorization-right checks.

The root-owned legacy plist/package path does not itself require Developer ID signing to describe unsigned LOCAL DEV installation; actual Installer/Gatekeeper policy and user consent must be tested separately on the agreed target. Developer ID signing/notarization for distribution is a separate enrolled Apple Developer Program/release identity path, not supplied by root ownership or an ad-hoc signature. Local SDK headers establish the API signing/notarization requirements, not membership eligibility, successful notarization or current account availability. No account/key inspection was done. Without network verification of enrollment details, do not promise a particular paid-account workflow. Nothing here supplies a trusted Apple release key pin, Apple-reviewed Core candidate, authenticated manifest or live compatibility evidence.

## Acceptance for this concrete choice

Offline next, only after contracts agreed: model duplicate commit/timeout/resume, gate publication before admission, start racing shutdown, dirty session without servicing journal, stale instance/session, release after commit, lost exit observer, rollback after candidate execution and two-stage removal. Model checks cannot prove macOS safety.

Core contract tests must demonstrate legacy-start fencing, root-only maintenance, durable failure results, interrupted resource acquisition/recovery and no VPN auto-start. Filesystem adapter tests inject write/flush/rename failure and malicious links/ACLs at every use. Service adapter fakes must distinguish disable, registration, process exit, control readiness and network cleanup as separate facts.

Separately authorized disposable-Mac acceptance must establish kernel identity/event association, process exit before replacement, persistent disable and independent startup gate, reboot at every boundary, account change, revoked consent/disabled service, actual cleanup failure, owner crash losing observer, candidate crash before result, rollback refusal and final removal. Exercise storage failure without claiming simulated fsync equals power loss. Signing/notarization and trusted delivery are later independent gates. No such tests were executed for this documentation change.

## Approved constraints and implementation boundary

1. **Hosting and authorization:** recommend separate root demand/boot LaunchDaemon plus explicit root CLI for DEV, keeping Core directly under launchd. Accept the extra root service and no GUI servicing initially, or choose a signed/notarized SMAppService track with its packaging/consent prerequisites. No automatic production implementation follows either choice.
2. **Recovery availability:** recommend fail-closed manual resume, and reboot plus Core recovery when exact exit observation is lost. Accept downtime/manual intervention, or fund a separate same-boot adoption/exit-proof design. Both retain cleanup proof and no auto VPN restore.
3. **Initial servicing scope:** recommend only future servicing-capable fresh installs, one retained prior artifact set, no owner self-update, and two-stage uninstall retaining the servicing tool until explicit finalization. Broader migration/full removal is additional reviewed work; current G installs stay fresh-only.

All three recommendations above are accepted for the offline model. They are not pending questions. Core contract details remain the proposed cross-repository review brief; those APIs are not implemented in Core. Trusted delivery remains blocked on provenance/pin/candidate work regardless of the three choices.
