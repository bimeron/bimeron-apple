# Authenticated unprivileged Core staging

Issue: [#31](https://github.com/bimeron/bimeron-apple/issues/31). The user approved option A (retain the three validated contents), verifier ownership of the evidence envelope, 0700/0600 output, disposable exclusive publication and the same-UID boundary after the memory discussion. The implementation is in `AppleCoreRelease.swift`, `AppleArchiveGate.swift` and `AppleCoreStaging.swift`. The earlier [proposal](safe-extraction-proposal.md) and `research/staging-memory/` remain historical design and small-fixture research, not the implementation contract.

This API stops at an unprivileged candidate. It does not execute a binary, install or update anything, authorize a candidate, choose a release version, supply a production trust pin, access a service, or establish readiness. Core `c04f20d575e4aed979b1024a32b421e7e5de1afe` remains proposed source selection only. Historical `e8de435` fixture results do not validate a `c04f20d` artifact. No app-facing delivery workflow is enabled by this library addition.

## Verification and ownership

`verifyManifest` first checks ingress limits, then explicitly copies the manifest, signature and supplied public key into independently owned `Data`. Signature verification and every subsequent interpretation use those copies. `verifyArchive` checks the declared byte count and archive cap, copies the archive, then hashes and parses that same owned snapshot. The snapshot operation is not an atomic read of a concurrently modified source; the signature/hash must authenticate the resulting snapshot. No later copy is taken from the original source.

`AppleArchiveGate` remains the sole ZIP interpreter and decoder. After the final required-entry check it returns exactly the three decoded contents it already inspected. The public `AppleCoreReleaseVerifiedArchive` has private construction and contains fixed roles, contents, counts, digests and the verified manifest descriptor. It no longer retains archive `data`. Stored entry slices are owned `subdata` copies and inflated outputs are owned decoder allocations; retaining them does not add a second decoded-payload copy. The archive snapshot becomes releasable when verification returns, though callers can still hold the original input. Static Mach-O/Go/version checks and all existing ZIP interpretation remain in the gate. In particular, ignored local-header name/flags/method values and unused input following the final DEFLATE block retain their existing semantics.

Only complete success can return a payload: a valid binary followed by an invalid or missing notice fails the entire operation. There are no successful per-entry callbacks, offsets, archive-supplied paths or extraction plans exposed to staging. The three canonical leaves are `bimeron`, `LICENSE` and `THIRD_PARTY_NOTICES.txt`.

The manifest descriptor privately binds the verifier-created `AppleCoreVerificationEvidence` to the selected archive fields. It retains the exact signed manifest and canonical signature, supplied public key and signed key identifier, app version/channel/architecture, independent approval tag/revision, verifier policy revision and caller-provided context. Compatibility fields and both archive identities remain available in the original authenticated manifest rather than an independently reconstructed envelope. The coordinator forwards the same descriptor unchanged.

Manifest bytes are bounded at 65,536, signature at exactly 89 and key at exactly 32. Each context string and each separately supplied app/channel/architecture/approval string is limited to 1,024 UTF-8 bytes before retention; existing stricter manifest/version validation still applies. Context records an explicit classification (`unspecified`, `syntheticUntrusted`, or caller-declared `independentlyConfigured`), approval identity, pin provenance and Apple build identity. These context values are caller assertions, not signed manifest fields, verified app-build provenance or new authorization. Default context is explicitly unspecified for existing callers. A supplied key does not itself establish an independent production pin. Synthetic tests explicitly carry synthetic classification through staging. No consumer may promote a classification or recorded success into independent trust.

## Filesystem contract and lifetime

The caller must provision an app-owned staging parent, keep exclusive authorized control of it and pass its absolute file URL when constructing `AppleCoreStagingCoordinator`. The library does not create or adopt an arbitrary candidate path. Filesystem checks establish ownership properties, not the identity or authorization of the caller's app. Parent acquisition walks from `/` using descriptor-relative no-follow directory opens. Ancestors must be owned by root or the effective UID and lack group/other write permissions; root-owned sticky ancestors such as `/private/tmp` are permitted. Every ancestor must have no ACL entries. The final parent must be owned by the effective UID, exactly 0700, have no flags and have no ACL entries. This deliberately strict policy rejects an ancestry containing even a restrictive ACL; callers must provision a compatible location rather than stripping an existing object's ACL. Retrieval errors other than Darwin's no-ACL result fail closed.

Each coordinator permits one active staging operation. It exclusively creates an unpredictable `.incomplete-<operation UUID>` directory, verifies its held descriptor and parent binding, then exclusively creates only the three fixed leaves relative to that descriptor. Files use `O_NOFOLLOW|O_EXCL|O_CLOEXEC`, remain nonexecutable 0600, and must be regular files owned by the effective UID with link count one, no flags and no ACL entries. The directory remains 0700. No archive permissions, owners, ACLs, timestamps, xattrs or other metadata are restored. An inherited ACL is rejected, not removed from an existing object.

Writes and SHA256 readback use at most 65,536 bytes per syscall. Short writes/reads and EINTR are handled; zero progress, overflow, unexpected counts, ENOSPC, read errors, writer close errors and hash mismatches fail. Counts are checked before each file and tracked through the writes; the gate also checks the aggregate count before decoding. The archive cap is 268,435,456 bytes, binary cap 268,435,456, each notice cap 4,194,304 and aggregate decoded cap 276,824,064. All three entries must be nonempty. Immediately before publication the coordinator rechecks directory/file identities, metadata, sizes, exact child names and every file's SHA256 from held read-only descriptors. Cancellation is polled before creation, each file, each write/readback chunk and immediately before publication. Authentication, parsing, one-shot inflation and other individual syscalls have no hard latency bound.

Publication uses same-parent `renameatx_np(..., RENAME_EXCL)` to `candidate-<operation UUID>`. There is no replacing rename or EXDEV fallback. Existing targets remain intact. This successful rename is the linearization point: subsequent cancellation returns the published candidate. Any subsequent confirmation failure throws `publishedButUnconfirmed` carrying the actual candidate and held descriptors for explicit reconciliation. It does not automatically delete the published artifact or retry publication.

A successful candidate holds its own parent, directory and three read-only file descriptors, observed device/inode identities, evidence, counts and hashes independently of coordinator lifetime. `withFileDescriptor` supplies a temporary duplicate outside the candidate lock; its closure must not close or retain the descriptor. A caller can use `pread` to avoid shared file-offset state. Reentrant disposal does not deadlock, and an already borrowed descriptor remains open through its closure. Successful `discard()` unlinks the owned artifact and closes all retained descriptors exactly once; repeated discard is harmless. If descriptor close reports an error after deletion, the candidate remains discarded and the error is reported without retrying a potentially reused descriptor. Deinitialization only closes remaining handles best-effort and leaves disk contents for reconciliation; it never performs implicit recursive deletion.

## Failure, crash policy and trust boundary

Before publication, cleanup checks the directory binding, ownership/metadata, exact known child set and every known file identity before deleting any child. It rechecks bindings before each descriptor-relative unlink and removes only the empty known directory. Unexpected children, replaced identities, changed directory ACLs or cleanup errors stop cleanup and report `cleanupIncomplete` with operation UUID, residual name and cause. No recursion, globbing, age-based removal, existing candidate deletion or input-archive deletion occurs. Residual names are diagnostic bookkeeping, not authorization to clean a pathname later. A changed parent or missing identity can intentionally leave the entire partial operation.

Atomic visibility is not crash durability. This implementation uses unbuffered writes and checks writer closes, but promises no fsync/power-loss durability. Staging is disposable: after a crash, a candidate name, digest or success record alone is never accepted. A caller must reconcile with appropriate ownership/evidence checks or begin a new operation; the library does not silently adopt leftovers or sweep stale directories.

These checks constrain other UIDs under the stated ownership assumptions. They do not solve malicious same-UID mutation, preexisting writable aliases or a compromised verifier process. A held read-only descriptor continues to view a mutable inode; chmod, link-count checks, hashes and a private directory do not make it immutable. A later privileged consumer must copy from held handles into root-controlled staging and revalidate the actual protected bytes, original signed evidence and its independently configured trust/approval/compatibility policy there. An unprivileged candidate is never S's protected Prepared state, installed state, running state or readiness proof.

## Validation and memory limits

The new synthetic signed tests cover both architectures, ignored hostile local names, complete-entry failure, external alias detachment before actual authentication, exact evidence binding, bounded I/O/cancellation, permissions, real/inherited ACL refusal, short/interrupted/zero-progress I/O, write/read/close/EXDEV failures, final hash revalidation, exclusive collision preservation, cleanup identity mismatch and unknown children, held-handle lifetime, deterministic disposal and one active operation. These fixtures are static test data and are never executed. The ingress tests first prove their no-copy buffers actually alias externally writable storage, then mutate manifest/signature/key/archive aliases after snapshot acquisition and before actual verification.

The external historical 348-vector corpus was initially absent from this checkout. A private copy supplied for this work is used with `BIMERON_APPLE_VECTORS`; tests refresh only that copy's signed sidecars. Those vectors are regression evidence for existing `e8de435` ZIP acceptance and rejection, including pinned Go interpretation, not release acceptance for another revision. Local tests need that environment variable to run corpus parity; an unset value causes an explicit XCTest skip. The existing CI policy and allowlists are unchanged.

Memory remains a material limitation. Maximum archive plus retained payload is 520 MiB; overlap with the caller's original archive adds another 256 MiB (776 MiB total), before parser slices, Mach-O section copies, evidence, allocator and runtime overhead. Archive release leaves up to 264 MiB retained payload. Chunked staging adds bounded readback storage and no complete payload copy, but these arithmetic byte budgets are not measured peak RSS. The previous small synthetic research measurements do not establish the integrated verifier's maximum RSS or a hard resource/time bound. Maximum-size allocation, live Core execution, root installation, crash/power-loss acceptance and privileged protected-copy integration are not validated by these tests.
