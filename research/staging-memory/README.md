Status: local prototype only. Local issue: determine whether U's retained decoded-content seam can be staged without another ZIP interpretation, and measure its allocation/retention costs without stressing the shared host. This is not approval for a production design, extractor integration, or S Prepared state.

## Proposed API, pending architecture approval

The future coordinator takes an explicitly owned archive snapshot before authentication. T authenticates and inspects that same snapshot, retaining exactly the three decoded owned contents it already inspected. It creates a private `VerifiedCorePayload` only after the complete archive succeeds, including final entry-set checks. No partial success callback crosses the seam. Staging accepts this payload, never archive paths, offsets, compression metadata, arbitrary entry names, or extraction instructions.

The result retains original authenticated manifest bytes, signature, key identifier, archive digest/size, version/architecture/revision, compatibility fields, independent approval identity, verifier policy and verification context. Per-role counts and digests bind the retained contents. The prototype uses clearly marked mock evidence, with no keys or real authentication; a boolean whole-archive fixture is not proof of authentication.

`stage(payload, coordinatorOwnedParent, cancellation)` returns a private `StagedCoreCandidate`: operation identity, original evidence, fixed names/counts/digests and held descriptors/observed identities. S receives only an unprivileged candidate. A protected consumer must copy the actual contents into its own controlled storage and revalidate bytes, original signature and its own trust/approval/policy configuration. A serialized success flag, pathname, digest, or mock envelope is not authority and cannot create Prepared state.

The canonical leaves are `bimeron`, `LICENSE`, and `THIRD_PARTY_NOTICES.txt`, all 0600 and nonexecutable inside a private 0700 candidate. Exact maxima are 268435456 binary bytes and 4194304 bytes per notice, 276824064 decoded bytes total. Reject before allocation/write when quotas, required count or whole-archive success fail. Cancellation is checked between bounded writes and immediately before exclusive publication. Cancellation observed after publication returns the published candidate. Rename collision preserves the existing destination and cleans only the owned incomplete candidate. Disposable staging does not imply fsync or crash durability.

## Ownership boundary

Swift `let Data` prevents reassignment, not mutation through externally owned NSData, no-copy or mapped storage. Ordinary Data value copies may share backing with copy-on-write; value mutation and independent byte ownership are different claims. Use an explicit copy from bounded bytes before authentication, then keep owned decoded contents private. Do not recopy an attacker-controlled source after authentication. Avoid a redundant full payload copy at staging: use bounded buffer views only for the duration of writes.

A read-only held FD resists pathname replacement but remains a view of a mutable inode. Writable descriptors and hard links can change its bytes. 0700/0600 and no-follow descriptor-relative operations restrict other UIDs under the stated ownership assumptions; they do not defeat a malicious same-UID process. Candidate descriptors are not immutable capabilities. No experiment here proves concurrent kernel safety, root safety, crash consistency or protected installation.

## Memory experiment policy

Initial inspection: host RAM 17179869184 bytes; vm_stat showed 4735 free 16KiB pages and 309907 compressor pages. Swap used approximately 862.56 MiB. `memory_pressure -Q` reported 56% system-wide free, showing why free pages alone are not an available-memory estimate. Despite reclaimable memory, deliberately cap experiments at 96 MiB live synthetic allocations per sequential fresh subprocess. Compiler/runtime RSS and allocator overhead are additional. Do not allocate maximum fixtures on this shared host.

The measured small fixture is an assumption for comparison, not a measured release. Report process RSS and peak separately from counted retained bytes. Page compression, allocator caching, CoW, compiler lifetime decisions, filesystem cache, and sampling affect results. No extrapolated RSS number is a measured maximum. Allocation counters exclude parser/inflater/Mach-O copies, runtime and other processes.

At the maximum, archive plus payload are 545259520 bytes (520 MiB) before copies/RSS. Retaining only payload after archive release is 264 MiB. Retaining archive plus payload plus a redundant complete decoded copy is 784 MiB. Retaining both original archive input and owned archive snapshot plus decoded output is 776 MiB; retaining both archive copies and two decoded copies is 1040 MiB. These are simultaneous logical byte budgets, not peak RSS bounds. The real parser could add compressed-entry/Mach-O section copies and transient overlap. Chunked writes avoid a new payload-sized staging buffer but cannot remove the 264 MiB retained payload requirement. Re-decoding from a retained archive using T's exact parser might lower retained output, but introduces a separate CPU/cancellation/interface tradeoff and is not implemented here.

## Decision to take through main

Provisional minimal recommendation: retain the three owned decoded contents from T, retain the bounded authenticated evidence, release archive storage once no parser consumer needs it, and stage through bounded writes without another payload copy. Benefit: one interpretation and decode. Drawback: up to 264 MiB retained output plus transient verifier memory, with maximum RSS still unvalidated. If that budget is unacceptable, discuss reuse of T's bounded decoder for a second decode from owned archive bytes; do not introduce another parser. Production ownership of the envelope (T versus coordinator), peak memory budget, cancellation during inflation, protected revalidation, metadata/ACL policy and disposable-versus-durable staging remain explicit decisions. The user authorized experiments only.

## Review clarifications and prototype gaps

Independent document review is retained in `review.md`. The full proposed contract also requires archive size 1–268435456, nonempty contents, checked sums and actual counts before each bounded write, at most one active operation per coordinator and one candidate/three files per operation. T owns actual inflation bounds and exact three/four ZIP-entry policy, including optional empty directory. The standalone synchronous prototype has no production coordinator or ZIP gate and does not validate these T obligations.

Publication must stay on the same filesystem with no replacement or EXDEV copy fallback. Cleanup must stop with `cleanupIncomplete` on unexpected children, identity mismatch or failure. A post-publication bookkeeping error needs a published-but-unconfirmed outcome carrying operation identity; this prototype has no throwing post-publication operation and does not implement that outcome. Cancellation checks occur at most every 64 KiB write/readback chunk. It does not bound T inflation latency.

Mock trust classification survives candidate handoff as `SYNTHETIC_UNTRUSTED_MOCK_AUTHENTICATION`. Mock evidence is a fixed small fixture, not attacker-supplied input. Production evidence byte/count limits are unresolved and must be agreed before any complete total-memory bound; all buffer arithmetic here excludes evidence. The prototype candidate retains evidence, counts and hashes, but closes handles before returning; the proposed production API's held-handle lifetime is not implemented. ACLs, ancestry traversal, xattrs/flags, hostile same-UID concurrency, fault injection, cleanup identity-race coverage and protected intake remain unimplemented. These omissions are not passed acceptance checks.

## Reproduction and measured results

Run `python3 research/staging-memory/run-memory.py` for sequential capped measurements. Raw phases, host observations, commands, three repetitions and caveats are in `memory-results.json`. Assumed fixture: 8 MiB archive, 12 MiB binary and two 0.25 MiB notices (12.5 MiB payload). Largest modeled live synthetic storage is 33 MiB, below the 96 MiB cap. Explicit additional owned-payload copies reached about 38.7 MiB peak RSS; COW retain, release and chunked modes reached about 26.1 MiB. These are process-specific small-fixture results. Owned mode deliberately mutates one byte per page to force private writable pages, so it is a copy-cost experiment, not integrity-preserving staging. Each mode already uses chunked writes; the chunked label is the no-extra-copy baseline, not a different inflater.

Releasing the archive reduces logical retention; allocator RSS need not fall immediately. The timing includes generation, sampling and buffered writes, excluding hashing/inflation and fsync, so it cannot predict full verification latency. No maximum-size experiment was run. Current RSS uses MACH_TASK_BASIC_INFO; peak uses Darwin getrusage. Physical footprint is not measured. See `prototype-results.txt` for standalone compilation/test commands; all generated binaries/module caches and filesystem fixtures belong in temporary directories.

Final independent code review is in `review-code.md`. Its P2 residual-reporting finding was corrected by the parent: every early open/fstat failure after mkdir and any cleanup failure reports `cleanupIncomplete(incompleteName)`, preserving uncertain state for reconciliation. The final parent build/assert run passed with a 131073-byte binary fixture exercising multiple chunks. The reviewer did not rerun tests; early filesystem failure classification was verified by source inspection, not fault injection. Review files retain their original findings as evidence, with this response recording the correction.
